# ADR-0001: Дані — файлами в Cloud Storage, кожен файл пише одна задача

## Status

ACCEPTED — ратифіковано власником 2026-10-18 (огляд M2).

Date: 2026-10-18

## Context and Problem Statement

ThinkHow зберігає проблеми людей (теми), розмови, карти проблем, кроки й оцінки, а також знання
системи (картки моделей мислення, пам'ять досвіду, стрічку змін) і роботу двигуна навчання.
Застосунок працює в Cloud Run, власний диск якого стирається під час кожного перезапуску. Масштаб —
власник і близьке коло (2–10 людей), ≤50 сесій на тиждень, мегабайти даних. Власник вирішив:
«текст пишеться файликами», «одна папка — свої файли, чітко розділені задачі».

## Decision Drivers

- Рішення власника: файли, а не база; папка користувача → папка теми → окремі файли під окремі задачі.
- G2: дані проблеми не губляться між сесіями й перезапусками.
- G3, G6: двигун навчання і власник змінюють знання; кожну зміну видно й можна відкотити.
- Cloud Storage не вміє змінити кілька файлів разом (немає транзакцій на кілька об'єктів).

## Considered Options

- A. Файли в Cloud Storage через клієнтську бібліотеку; **кожен файл пише одна задача**.
- B. Cloud Storage як «змонтована тека» (FUSE).
- C. Filestore (мережевий диск із блокуваннями).
- D. Реляційна база (Cloud SQL) або Firestore.
- E. Один файл на тему з усім разом, з умовними записами («заміни, лише якщо ніхто не змінив»).

## Decision Outcome

Chosen option: **A**, бо це рішення власника і воно прибирає одночасні записи в один файл без
жодних блокувань.

- Два bucket-и в `europe-west3`: `users` (теми людей) і `system` (знання, навчання). Завдання
  навчання має право лише читати `users`.
- Папка теми `users/<людина>/<тема>/`: `conversation.md` (пише задача «відповідь на репліку»),
  `map.json` (та сама задача; фаза й обраний крок), `routing.json` (задача «вибір методу»),
  `steps.json` (людина, коли відповідає на питання).
- `system/knowledge/changes/<rev>.json` — пише лише завдання навчання, «лише якщо ще немає»;
  `system/knowledge/rollbacks/<n>.json` — пише лише власник; ревізія знань — пара (`rev`, `n`).
- Старі версії файлів увімкнено — захист від перезапису (не резервна копія; копія поза проєктом
  відкладена — `tasks/proposed/103-backup-before-volume.md`).

### Consequences

* Good, because немає бази, блокувань і умовних записів спільних файлів; дані — звичайні файли.
* Good, because завдання навчання фізично не може зіпсувати дані людей (права на bucket).
* Bad, because рідкісне подвійне надсилання з двох вкладок перезаписує `conversation.md` (останній
  запис перемагає); прийнятий залишковий ризик — перезаписане лишається в старих версіях.
* Bad, because довільні запити по тисячах сесій були б повільні; за цього масштабу — ні. Перенести
  файли в базу пізніше дешево.

### Confirmation

- M3: тест, що до bucket-а `users` звертається лише модуль сховища, і тест, що одна людина не
  читає файл іншої.
- Walking skeleton перевіряє PR-07 (файли пишуться й читаються з Cloud Run).

## Pros and Cons of the Options

### B. FUSE
* Good, because «просто файли» без коду сховища.
* Bad, because немає блокувань і атомарного створення «лише якщо ще немає» для `changes/<rev>`.

### C. Filestore
* Good, because справжні файли з блокуваннями.
* Bad, because мінімальний обсяг коштує на порядки більше за потрібне (Q2).

### D. База
* Good, because транзакції і довільні запити («нудний» вибір playbook §1).
* Bad, because власник обрав файли; на сотнях файлів база нічого не дає.

### E. Один файл на тему з умовними записами
* Bad, because відкинуто власником: різні задачі пишуть різне й заважали б одна одній.
