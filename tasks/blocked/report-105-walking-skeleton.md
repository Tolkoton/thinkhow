- **Є прототип ThinkHow, який працює від початку до кінця.** Ланцюжок такий:

  - людина завершує сесію;

- Увесь ланцюжок перевірено локально, автоматичним тестом `tests/smoke/test_e2e_local.py`. Справжні виклики моделі
  перевірено окремими live-тестами. Premise PR-09 тепер `verified`: частини стикуються без переробки контрактів.
- **У хмарі ще нічого не розгорнуто.** Задача так і визначала: розгортання робите ви. Покрокова інструкція й чекліст

  (файли в Cloud Storage). Тому задача в `blocked/`, а не в `done/`.
- Код складається з частин архітектури M3 (`platform`, `knowledge`, `facilitation`, `access`, `workspace`, `web`,
  `learning`). Чотири запобіжники A3 (AC4) — автоматичні тести, і всі зелені: `tests/test_ac4.py`.

## Демонстрація на хвилину (локально, без хмари)

```bash
cd ~/projects/thinkhow
THINKHOW_LOCAL=true THINKHOW_LOCAL_DIR=/tmp/thinkhow-demo THINKHOW_OWNER_EMAIL=owner@localhost \
  PYTHONPATH=src .venv/bin/uvicorn thinkhow.web.app:app --port 8080
```

1. Відкрийте `http://127.0.0.1:8080/` і створіть тему, напишіть репліку. Відповідь у локальному режимі сценарна —
   «(локальний режим) Уявіть, що план провалився…», — але йде потоком так само, як справжня. Далі натисніть
   «Завершити сесію».
2. В іншому терміналі запустіть аналіз:
   ```bash
   THINKHOW_LOCAL=true THINKHOW_LOCAL_DIR=/tmp/thinkhow-demo PYTHONPATH=src \
     .venv/bin/python -m thinkhow.learning.job analyze
   ```
   Після цього в `/tmp/thinkhow-demo/system/learning/observations/` з'явиться файл спостереження. Його поле `link`
   відкриває вашу репліку.
3. Справжню модель можна побачити так: `.venv/bin/python scripts/smoke_test_skel_facilitation.py` веде одну репліку
   за Pre-mortem через Vertex на `eu`.

## Рішення, які я ухвалив сам

Усі ці рішення — двосторонні двері. Кожне записане AUTONOMOUS у `.engine/overseer/escalations.md` або в ADR.

1. Робочий цикл:
   - продовжив роботу з гілки `wip/105-walking-skeleton/20261022T142339Z`: файли взяв `git checkout <гілка> -- <шляхи>`,
     бо `cherry-pick` вимагає дозволу;
   - друге блокування cold-reader-а на slice виправляв у контракті без третього прогону: skel-facilitation,
     skel-workspace, skel-web, skel-learning, skel-guards-deploy.
2. Імпорти й запобіжники:
   - **ADR-0003**: фасилітація доходить до сховища лише через Знання; у контракті import-linter — один названий виняток
     замість послаблення. Amendment 1 — так само для навчання й типу `Identity`;
   - `workspace` імпортує лише `thinkhow.facilitation.types`, і ці типи не залежать від `platform` (Q6 skel-facilitation).
3. Модель і інструкції:
   - інструкція фасилітатора — дослівно PoC 101, змінено два рядки: якір репліки `t<n>` замість «s2#n», приклад id «i3»
     замість «t3»;
   - якір спостереження в схемі виклику — `enum` номерів реплік сесії, тож модель не може назвати неіснуючу репліку;
   - сценарна модель локального режиму: фіксована відповідь у формі справжньої.
4. Сесії та розмови:
   - **ADR-0004**: формат `conversation.md` — markdown із прихованими маркерами; будь-який текст людини читається назад
     без змін;
   - власник **читає** чужі теми, але не пише в них (Q2 skel-workspace) — питання 4 у файлі задачі;
   - репліка без відповіді лишається в закритій сесії; нова репліка після закриття відкриває нову сесію;
   - сесія, закрита 24 годинами тиші, визначається при читанні, а не записом маркера.
5. Веб і помилки:
   - кістяк без HTMX: свій JS на 160 рядків (`static/conversation.js`);
   - тексти помилок і підписи на сторінках — мої (escalations.md, skel-web-wording);
   - помилка однієї сесії не валить завдання навчання: вона йде в журнал, і наступний прогін пробує знову.
6. Розгортання:
   - `--max-instances 1`; `--task-timeout 3600s` для Job;
   - `seed` — перед розгортанням сервісу.
